# HXMT/HE 搜索的未决项

### 1. 单路探测器占比上限是 v6 目录之后才加的（2026-09-06）

18 路 CsI 合成一路搜索，单个 PMT 的毛刺没有别的判据能挡。四个仪器共用的判据
`blink_algorithms::detector_share::MAX_DETECTOR_FRACTION = 0.8`（最显著一格里一路
探测器占比超过 0.8 即否决）已接进 `search`，计入 `dropped_single_detector`。它对
SVOM 是实证过的（占比 > 0.8 的候选闪电关联 0/12，≤ 0.6 的 42%），对 GRID 抓到的是
一路探测器自己在闹的日子。

**v6 目录（4270 显著、目录 5421）是在没有这条判据时产出的。** 审计（2026-09-06，
`blink acd-audit --scint csi` 加 `det_share_max` 列，按候选 start/stop 整窗、1K 事例）：
4270 个显著候选全部审到，单路最大占比分布 0.0–0.1 有 879、0.1–0.2 有 3175、0.2–0.3
有 197、0.3–0.4 有 16、0.4–0.5 有 2、0.5–0.6 有 1，**0.6 以上一个都没有**（窗内计数中位
49，18 路均分的期望 0.06）。判据对 v6 显著候选零影响，不重跑。目录 B 层（fa ≤ 1 且关联，744 个）
同样审过：占比 0.1–0.3 占 721 个、0.3–0.4 有 12 个，**0.4 以上一个都没有**（窗内计数中位 17）。目录里不在显著表的其余 1106 个显著行也审了：最高 0.417，
0.5 以上没有。**整个 v6 目录（5421 行）对这条判据免疫，结案。**表在 `/scratchfs2/gecam/guohx/v6run/audit_det/audit_det_v6.csv`，
本地 `scratch_gbm/hxmt_audit_det_v6.csv`。

### 2. v6 目录里 1720 个"无星历"候选其实只缺姿态，重跑后全部回来（2026-09-06）

`Signal.attitude` 改成可选之后，只重跑 v6 里出现过 `dropped_no_ephemeris` 的 129 天
（`v6run/attcheck/`，v8 二进制）：旧 65005 个候选，新 66725 个，恰好多出 1720 个、每个
都没有 `attitude` 字段，`dropped_no_ephemeris` 归零，其余候选逐个相同。也就是说 v6 的
星历表缺的是姿态（att 文件比轨道文件短），位置一直都在；这些候选多在成片的时段里
（如 2017-10-20 15:05–15:33），其中至少一个显著（2018-01-23T11:06:15.711，fa 4.0e-6）。
处理：对 attcheck 输出跑闪电关联，把新增候选并入 `tgfs_v6b.json`（1711210 条），用
`blink catalog` 出 `catalog_v6b.csv`（v6 原件不动）。新增 1720 个里显著 11 个、闪电关联
3 个；目录 5421 → 5432（+11：direct 10、lightning 1）。最显著的几个（2024-07-16
fa 1e-36 / 53 计数、2023-03-23 1e-32 / 49、2024-04-13 1e-30 / 39）计数偏多、无闪电，
要按 REP 那套（列车密度、|lat|、ACD）过一遍再定性。论文用 v6 还是 v6b 由用户定；
v6b 是 v6 的严格超集。

### 3. 微秒截断在 HXMT 上不发作，但不是因为写法对（2026-09-10）

全项目 16 个 cluster 脚本里的 `met()` 把 ISO 小数秒截到微秒
（`(frac + "000000")[:6]`，`datetime` 只到微秒）。HXMT 侧逐条查过：

* 候选表 `start`/`stop` 是 chrono 的 9 位纳秒串，**8458/8540 个端点是 9 位有效
  数字，只有 0.96% 恰好落在整微秒上**。截断会把每个端点平均前移 775 ns
  （中位 959 ns）。
* 而候选窗端点就是事例时刻本身（`Candidate::new(data[cursor].time(),
  data[cursor + step].time())`），所以截断 `stop` 会直接丢掉边界那个事例。
* **实测**（25 个候选最密的小时、732 个候选，同一个 `blink acd-audit` 跑两遍，
  唯一差别是输入 CSV 的 start/stop 截到微秒）：命中率 **29.5%**——216 行不变、
  514 行少 1 个事例、2 行少 2 个；平均少 0.708 个，相对 0.33%（这批 `n` 均值
  211；按全量 4270 的 `n` 中位 49 算，少 1 个就是 2.0%）。`det_share_max` 有
  45.9% 的行会变（最大变化 0.083）。
  机制按 `stop` 端点的纳秒余数完全分层：**余数 < 20 ns 丢 0%，20–50 ns 丢
  8.8%，≥ 50 ns 丢 100%**——MET 1.7e8 s 处 f64 的 ulp 是 30 ns，截掉不到半个
  ulp 的量会往回舍成同一个浮点数，超过就实打实丢掉边界那个事例。
* **但 HXMT 的结论没受影响，因为没有一条 HXMT 复算路径走那个 met()。**
  唯一带这个写法的是 `scripts/cluster/attcheck_compare.py`，它只拿 met 做两张
  候选表 ±1 ms 配对，两边同样截断、误差抵消（已一并改成正确写法）。真正的
  复算路径 `blink acd-audit` 是 Rust，chrono 全精度解析，**4270 行的审计计数与
  搜索时逐个相同，5 列 ACD 计数全 0 差**。其余中间表（`make_sig_all_v6.py`、
  `sig_train_v6.py`、`build_audit_list.py`、`extract_tgfs_v6.py`）全是把 9 位串
  原样搬运。`scripts/` 里 20 处 `[:23]`/`[:26]` 切片没有一处切的是 HXMT 候选时刻。
* **阈 34 不受影响**：`neighbors_10min` 在 Rust 里用 `timestamp_micros()` 数
  ±600 s 窗，微秒量级的误差与判据差 9 个数量级。

顺带钉死一条对账口径：**HXMT 的 `count` 不等于 `[start, stop]` 窗内计数**。
`Candidate::merge` 把 `stop` 取并、`count`/`mean`/`sf`/`bin_size_best` 取最显著
子窗（实测 `n − count` 中位 15）。要对账，用 `acd.n` 对 `[start, stop]`，或用最佳格
`[start + delay, start + delay + bin_size_best]` 对 `count`，两套别混。

### 4. 同一物理事件的重复计数：管线里已有两级归并，残留 1.7%（2026-09-10）

* **严格重叠的候选 HXMT 一对都没有。** 共用的 `snapshot_stepping` 每找到一个
  候选就跟 `result.last()` 比 `Candidate::mergeable(&current, 0.0)`（条件
  `self.stop >= other.start`），成立就 `merge`。实测 4270 显著行、5421 目录行
  各 0 对重叠。
* **亚秒堆积有，但几乎全在列车里。** 按 1 s 归并成 episode：全部显著
  4270 → 3633（压缩 14.9%）；其中 `is_train = 1` 的 699 个 → 97 个
  （压缩 **86.1%**），`is_train = 0` 的清洁池 3571 个 → 3536 个（压缩 **0.98%**）。
  亚秒堆积与分钟级列车是同一批物理事件（REP 微暴），阈 34 虽按 ±600 s 定标，
  实际把亚秒堆积一并摘了。
* **残留**：最终目录 5421 → 5328 episode（−93，**−1.72%**；direct 4677→4585，
  lightning 744→743）。61 个多成员 episode，跨度中位 11 ms、p90 84 ms、
  最大 0.635 s，分散在几十个日期（最多的一天 2 个），154 个成员里 17 个闪电关联。
* **判为不该归并**：TGF 本身有 ms 级多脉冲结构，跨度中位 11 ms 的两三个候选
  很可能是同一次 TGF 的两个脉冲，那是物理不是伪影。**但速率推算要记账**：
  `estimate_tgfs_v6.py` 的幂律归一来自清洁池 fa ≤ 1e-8 那一段（3571 个），
  这一段按 episode 计压缩 **0.98%**，所以 Estimated TGFs 13,547 若改按物理事件
  计数约降到 **13,410**。目录本身（5421）的压缩是 1.72%，两个数别混：一个是
  目录行数，一个是速率推算的拟合输入。

### 5. 逐路探头计数已随候选保存（2026-09-10）

`blink_core::DetectorCounts` 在 HXMT 上从 `None` 改成填实值
（`algorithms/detectors.rs`）：18 路（`Det_ID` 0..17）在候选窗与基线窗内的计数。
窗口定义与 `acd_counts` 逐字一致，于是 `sum(window) == acd.n`、
`sum(baseline) == acd.n_bg`，两个量互为校验。

值得填的三条理由：（1）`MAX_DETECTOR_FRACTION = 0.8` 是四仪器共用的定值，接进
HXMT 时只在 4270 个显著候选上审过（最高 0.417），存下整条向量，阈值日后复议
不必重跑全量；（2）18 路本底率实测差一成（一小时 1.86M–2.06M），只看窗内计数
分不清"这一路亮"和"这一路本来就快"；（3）18 路装在同一块板上、高能光子穿过结构
时相互遮挡不同，相对计数携带入射方向——**侧向电子直接打进边上的 CsI 会让照亮
明显不对称，而从上/下方来的伽马接近均匀**，这正是第 6 条那个未决问题的判别量。

**v6 目录本身没有这一列**（`#[serde(default)]`，旧文件读回为 `None`），不重跑。
补救办法是 `blink acd-audit` 新增的 `det_window`/`det_baseline` 两列：拿冻结的
候选表离线复算，不动搜索。
