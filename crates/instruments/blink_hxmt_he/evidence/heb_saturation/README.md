# HEB 暴表源窗内的饱和普查

对 `HEB_list.xlsx` 全部 **832** 条，逐条检查 `[Trig+src_start, Trig+src_stop]` 窗内
HXMT/HE 有没有饱和。一并查出并修掉了 `detect.rs` 两道关卡共有的一处量纲错配。

## 结果

| | 条数 |
|---|---|
| `saturated`——窗内至少一次 FIFO A 复位，有真实数据丢失 | **141** |
| `clean`——两个数据产品里都没有洞 | **691** |

其中 **137 条由判据判出**，4 条手工并入（1 条判据仍拒、3 条 1B 无覆盖改判 1K），
`note` 列逐条注明。

14513 条复位，总死时间 182.7 s，其中 221009A 一条占 128.2 s（1.15e7 事例）。
其余 140 条合计 54.5 s。受影响箱体：单箱 88、双箱 25、三箱 28。

## 怎么查的

对每条暴的**绝对 MET 窗**跑两件独立的事（839 个归档小时任务；7 条窗跨小时，
两个小时都跑取并集；221009A 的 `src_*` 列是 `-`，改用 `tstart/tstop` = −50…+2000 s）：

1. `blink sat detect` —— 1B 逐包时间重建出的 FIFO 复位，**权威判据**。
2. `blink sat dump packets` —— 逐包事例率，积出 FIFO 队列占用。MCU 以
   109 事例 / ~7 ms = 15571 evt/s 抽空 FIFO A，容量 455 事例（M67204H，
   4096×9 bit，每事例 9 字节）。**所有非饱和窗的积压峰值 ≤ 350**，
   即没有被漏掉的持续斩波（`detect.rs` 注释里那个已知盲区）。

外加 `blink sat extract --source 1k` 在同样的窗上跑一遍做独立对照：
凡 1B 判饱和的窗，1K 事例流里洞的总长与 1B 逐包洞的总长**逐条相等**
（相对差中位 0.0000）。

**18 条窗口 1B 归档无覆盖**（文件在，但该小时事例流不含这一段；1K 有数据，
已核对）。这 18 条改用 1K 判定，`judged_on` 列标注。其中 HEB240118075、
HEB250824475 判饱和，其余 16 条干净。

## 顺带查出的判据缺陷（已修）

一个空洞要判成 FIFO 复位得连过两关，而**两关量到的都是整包平均**：
`MCU_READ_RATE_FLOOR` 闸门比的是 `event_rate = n_events / span`，`GAP_FACTOR`
的基线是 `mean_event_interval = span / n_events`。更糟的是闸门还在 **±5 个包**
的范围里取最大。本底率下一个包横跨约 27 ms，所以这个平均把毫秒尖峰稀释约十倍，
而 ±5 包意味着测量点离空洞可以有几百毫秒（中断段里一个包能横跨 108 s，就是几百秒）。

两关因此一起漏检：洞长约等于 455/尖峰率，门槛约等于 100/包级率，
要通过就得「包级率 ≥ 尖峰率的 22%」。

现在两关共用**一个**量，从事例时间读，**只看洞旁边**：

```
rate = max(洞前最后 16 个事例的率, 洞后最前 16 个事例的率)
闸门:  rate >= LOCAL_RATE_FLOOR
基线:  gap > GAP_FACTOR / rate
```

`peak_rate`（整包滑窗峰值）和 ±5 包加宽都删掉了。±5 包是旧写法的遗留：一个包
只给一个率，只能靠横向多取几个包压涨落；换成事例级窗口后一个包里就有约 109 个
测量，这个理由不成立。

### 阈值怎么定的

`LOCAL_RATE_FLOOR` **不是物理阈值**。泊松否决已经由 `GAP_FACTOR` 承担
（100 倍平均间隔是 e⁻¹⁰⁰），闸门真正要挡的只是中断段那类低速率长洞。而且记录
下来的率是被审查过的下界——FIFO 一满就堵写，堵掉的事例恰恰不在数据里，拿物理值
（15,600）去卡一个系统性偏低的观测量只会漏检。

12 个整小时上扫（含 SAA 进出、断档小时、221009A、2024-05-11 斩波小时）：

| 阈值 evt/s | 检出 | 相对旧判据 |
|---|---|---|
| 500 / 1000 / 2000 / 3000 / 4000 / 6000 / 8000 | 27526（逐条相同） | **+67, −0** |
| 10000 | 27523 | 开始丢 |
| 12000 | 27503 | −20 |
| 15000 | 27109 | **−406** |

500 到 8000 跨一个多数量级结果一字不差，判据对阈值不敏感。15000 丢掉的 406 条
都在斩波段：洞旁那 16 个事例的率到不了 15 kHz，旧判据是靠 ±5 包在几百毫秒外找到
的尖峰才放行的。取 **2000**——比中断段包的 1–19 evt/s 高两个数量级，比低速率箱的
约 400 evt/s 高 5 倍，比平台上沿 8000 低 4 倍。任何阈值下都没有出现起止落在整秒的
空洞，也没有 >50 ms 的。

### 中途试错，留档

* **整包滑窗峰值做基线**：12 小时上多出 6 条起止落在整秒的 1.000 s「空洞」。
  中断段的包横跨 5.8 s、12.9 s 甚至 108 s 才凑够 109 个事例（率 1–19 evt/s），
  里面只要有 16 个事例挤在一起，整包峰值就虚高、基线塌到极小。同一版还多出 8 条
  1.5–4 ms 的洞，也非 FIFO 尺度。这正是后来发现闸门里 `peak_rate` + ±5 包
  是同一个构造的线索。
* **`MCU_READ_RATE_FLOOR` 一名两用**：`reconstruct_gaps` 在 gap 两端都估不出率时
  拿它当形状函数的地板填充值。检测阈值下调时差点把重建的填充率一起改掉，
  已拆成两个常量。

### 验证

* 12 个整小时：**+67 条、−0 条**，66 条落在 15.1–20 ms，另 1 条 39.9 ms。
* 抽样的新增条目在 1K 事例流里逐条复现，长度一致到 0.01 ms。
* 832 个源窗：**17 个窗由 `clean` 变 `saturated`，反向 0 个**。

### 还漏一条

`HEB211105190`（洞 11.87 ms，这批里最短，1K 同样看得到）判据仍然拒：要过
`GAP_FACTOR` 得边缘率高于 8425 evt/s，它不够。旧判据也没检出它，所以不算回退。
按「宁可误报不许漏检」，表里仍按 `saturated` 记并注明代码找不到它。

## 一个未决的问题：弱端的复位不是 GRB 造成的

对 46 条「窗内只有一次孤立复位」的样本，看未复位的另两个箱：

| | 缺口应有计数 | 洞后 100 ms 超出 | 未复位两箱的超出 |
|---|---|---|---|
| 46 条孤立复位 | 4438 | 11773（2.65×） | — |
| ↳ 两箱看到 >5σ 对应（20 条） | 2324 | 5499 | +1601 |
| ↳ 两箱什么都没有（26 条） | 2115 | 6274 | **−398** |

复位确实伴随真实变亮（超出是缺口的 2.65 倍，不是单纯把事例挪了时间），
但 **26/46 条这个变亮只出现在复位的那个箱**。三个箱看同一片天，
所以那些复位的触发源不是 GRB 光子。洞是真的，成因未定。

这影响的是「GRB 有没有把 HE 打饱和」，不影响「窗内有没有数据缺口」。
最亮那批（221009A、190114C、211211A、200415A、260226A，三箱几百次复位）
不在此列。全 141 条的对应性拆分尚未做。
