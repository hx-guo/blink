# HEB 暴表源窗内的饱和普查

对 `HEB_list.xlsx` 全部 **832** 条，逐条检查 `[Trig+src_start, Trig+src_stop]` 窗内
HXMT/HE 有没有饱和。一并查出并修掉了 `detect.rs` 速率闸门的一处量纲错配。

## 结果

| | 条数 |
|---|---|
| `saturated`——窗内至少一次 FIFO A 复位，有真实数据丢失 | **141** |
| `clean`——两个数据产品里都没有洞 | **691** |

14509 条复位，总死时间 182.6 s，其中 221009A 一条占 128.2 s（1.15e7 事例）。
其余 140 条合计 54.4 s。受影响箱体：单箱 71、双箱 25、三箱 26（按修正前的
122 条统计，量级不变）。

## 怎么查的

对每条暴的**绝对 MET 窗**跑两件独立的事（839 个归档小时任务；7 条窗跨小时，
两个小时都跑取并集；221009A 的 `src_*` 列是 `-`，改用 `tstart/tstop` = −50…+2000 s）：

1. `blink sat detect` —— 1B 逐包时间重建出的 FIFO 复位，**权威判据**。
2. `blink sat dump packets` —— 逐包事例率，积出 FIFO 队列占用。MCU 以
   109 事例 / ~7 ms = 15571 evt/s 抽空 FIFO A，容量 455 事例（M67204H，
   4096×9 bit，每事例 9 字节）。**所有非饱和窗的积压峰值 ≤ 350**，
   即没有被漏掉的持续斩波（`detect.rs` 注释里那个已知盲区）。

外加 `blink sat extract --source 1k` 在同样的窗上跑一遍做独立对照：
凡 1B 判饱和的窗，1K 事例流里洞的总长与 1B 逐包洞的总长**逐条相等**
（相对差中位 0.0000）。

**18 条窗口 1B 归档无覆盖**（文件在，但该小时事例流不含这一段；1K 有数据，
已核对）。这 18 条改用 1K 判定，`judged_on` 列标注。其中 HEB240118075、
HEB250824475 判饱和，其余 16 条干净。

## 顺带查出的判据缺陷（已修）

`detect.rs` 的 `MCU_READ_RATE_FLOOR` 闸门问的是「瞬时入口率有没有超过读出率」，
量到的却是 `event_rate = n_events / span`——**109 个事例的平均率**。本底率下
一个包横跨约 27 ms，撑满 FIFO 只要几毫秒的爆发，这一平均把毫秒尖峰稀释约十倍。

实测代价（832 个源窗，共 6.4 小时）：满足 `gap > 100×baseline` 且 `≤ 1 s` 的空洞里，
14478 条通过闸门、**25 条被整包平均率挡掉**。被挡掉的 25 条全部落在 15.6–17.9 ms，
与通过的那批同一段；>100 ms 和 <10 ms 都是 0 条——闸门没有挡住任何**另一类**东西，
只是切掉了同一人群的低速率尾巴。

改为包内 16 事例滑窗峰值（`peak_event_rate`）。验证：

* 12 个整小时对照（含 SAA 进出、断档小时、221009A、2024-05-11 斩波小时）：
  **只增不减，+54 条**，全部 15.1–18.8 ms，长洞 0 条。
* 最安静那小时新增的 10 条，1K 事例流逐条复现，长度一致到 0.01 ms。
* 832 个源窗里 16 个由 `clean` 变 `saturated`。

**为什么能确认这批不是误报**：洞长应当等于 FIFO 容量除以入口率。这 19 条
（洞 11.9–17.5 ms ⇒ 需 26–38 kHz）与 46 条早已判饱和的孤立复位
（需 9–30 kHz）在「洞长 vs 实测 1 ms 峰值率」平面上完全重叠，前者的
实测/所需比值中位 0.81、后者 0.63（实测是下界：FIFO 一满，后面的事例根本没进来）。

### 还剩一处，没改

`GAP_FACTOR = 100` 的 `baseline` 用的也是 `mean_event_interval = span / n_events`，
同一个包级平均量。通过条件等价于「包级率 ≥ 尖峰率的 22%」（洞长 ≈ 455/尖峰率，
门槛 ≈ 100/包级率），尖峰被摊薄十倍就过不去。

`HEB180405168`（洞 16.74 ms，baseline×100 = 22.6 ms）和 `HEB191108003`
（洞 16.70 ms，24.6 ms）卡在这里，1K 能看到同样长度的洞。表里按 `saturated` 记，
`note` 列写明**代码找不到它们**。`GAP_FACTOR` 是主要的误报防线，不要只凭这两条
个案去动它。

## 一个未决的问题：弱端的复位不是 GRB 造成的

对 46 条「窗内只有一次孤立复位」的样本，看未复位的另两个箱：

| | 缺口应有计数 | 洞后 100 ms 超出 | 未复位两箱的超出 |
|---|---|---|---|
| 46 条孤立复位 | 4438 | 11773（2.65×） | — |
| ↳ 两箱看到 >5σ 对应（20 条） | 2324 | 5499 | +1601 |
| ↳ 两箱什么都没有（26 条） | 2115 | 6274 | **−398** |

复位确实伴随真实变亮（超出是缺口的 2.65 倍，不是单纯把事例挪了时间），
但 **26/46 条这个变亮只出现在复位的那个箱**。三个箱看同一片天，
所以那些复位的触发源不是 GRB 光子。洞是真的，成因未定。

这影响的是「GRB 有没有把 HE 打饱和」，不影响「窗内有没有数据缺口」。
最亮那批（221009A、190114C、211211A、200415A、260226A，三箱几百次复位）
不在此列。全 141 条的对应性拆分尚未做。
