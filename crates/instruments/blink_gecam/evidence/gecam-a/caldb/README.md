# GECAM-A 的 CALDB 到底维护到什么程度

2026-09-10 实测 `/gecamfs/soft/CALDB/`。

## 先解开那个矛盾

`readme.txt` 里有一条 **v1.0（2021-08-31）「删除GECAM A星的内容 data/gecam-a/*」**，
读起来像是 A 星标定被废弃了。**这条是 2021 年 8 月写的，不是现在的状态**：
A 星第一批事例数据是 2022-10-21，2021-08 时载荷还没出数，删掉的是发射前的占位内容。

目录现在不但在，还在持续维护——`data/gecam-a/grd/caldb.indx` 20 MB、mtime **2026-07-17**。

真正的转折点是 readme 里这条（原文照录）：

> **2025-05-13**
> 把标定程序升级到V3版本，能够同时对A星和B星标定EC！！！！！！！！！
> 目前处理的是2025年01月~04月的数据

之后 2026-06-21、2026-07-17 两条都写明「含A星和B星」。
`log_GECAMB.txt` 是 readme 的一份旧快照（截止 2022-02-24），没有 A 星专属日志，
所以「A 星没有日志」不代表没维护，只是 A 星的记录混在 B 星那份 readme 里。

## 逐项实测

`/gecamfs/soft/CALDB/data/gecam-a/grd/bcf/`：

| 子项 | 文件数 | 最新 mtime | 时间覆盖 |
|---|---|---|---|
| `c2e`（能量刻度 EC） | 450 | 2026-07-17 | **只有 9 个 epoch**，见下 |
| `det_status` | 50 | 2025-05-19 | 单版本 |
| `lut`（并道表） | 200 | 2021-12-10 | 发射前；并道表不随时间变，不算问题 |
| `mc_rsp`（方向响应） | 10025 | 2025-05-19 | 401 方向 × 25 路，**齐全** |
| `pi` | 50 | 2023-01-10 | 单版本 v01 |
| `reso`（分辨矩阵） | 50 | 2025-05-19 | 单 epoch `1971/01/01` |

`c2e` 的 9 个 epoch：

```
1971/01/01     <- 默认/占位
2025/01/01  2025/02/01  2025/03/01  2025/04/01
2026/03/01  2026/04/01  2026/05/01  2026/06/01
```

450 = 9 epoch × 50（25 路 × 高/低增益两档），对得上。

对照 **GECAM-B 的 `c2e` 有 67 个 epoch**，从 `2019/01/01`（发射前）、`2020/12/24`
（发射后立刻）一路密集到 `2026/06`。

## 三个空缺

1. **2022-10 .. 2024-12 没有在轨 EC**，只有 `1971/01/01` 那份默认。
   而这段正好是 A 星唯一落在 WWLLN 库（止 2024-12-31）覆盖内的部分。
2. **2025-05 .. 2026-02 也是空的**（`2025/04` 之后直接跳到 `2026/03`）。
3. **CPD 的 `c2e` 只有 `1971/01/01` 一个 epoch，从来没做过在轨能量标定。**
   这条与数据侧自洽：A 星的 CPD 事例产品 2025-03-12 才开始出，2026 年之前无数据可标
   （见 `../coverage/README.md`）。

方向响应 `mc_rsp` 反倒是齐的，401 方向 × 25 路都在，
所以 OPEN-QUESTIONS 第 13 条的第二档（似然定位）在原料层面 A 星不缺。

## LEVEL1 产品线的版本落后：EBOUNDS 溢出道

A 星的 LEVEL1 EBOUNDS **全程** `ch448` 的 `E_MAX = 0.0`，而 B 星全程 `20000.0`。
抽查 9 个 epoch（2022-10-21 / 2023-06-16 / 2023-12-20 / 2024-01-11 / 2024-09-06 /
2024-12-31 / 2025-01-17 / 2025-06-15 / 2026-06-01，文件 DATE 从 2023-01-21 到 2026-06-21），
**无一例外**：

| 项 | GECAM-A（9 epoch） | GECAM-B（3 epoch 对照） |
|---|---|---|
| 道数 | 498 | 498 |
| ch0..447 梯子连续 | True | True |
| ch0 | 2.00–2.18 keV | 2.00–2.18 keV |
| ch54 | 39.1–40.2 keV | 39.1–40.2 keV |
| ch447 | 9921.0–10053.5 keV | 9921.0–10053.5 keV |
| **ch448 `E_MAX`** | **0.0** | **20000.0** |
| 溢出行数 | 50 | 50 |

这是产品线版本差异，不是数据损坏。readme 里两条对上了号：

> v0.9　pi：最后50道超高不再从read_highlow_threshold_kev读取并计算，而是直接填0.
>
> 2022-01-14　软件重大更新。之前50道超高都赋值0，现在下阈改为4096道对应的能量；
> 上阈改为20MeV。响应矩阵生成器也因此改变。

B 星跟进了 2022-01-14 那次升级，A 星没有——A 星的 `pi/` 只有 v01 一版、mtime 2023-01-10，
一直在用旧生成器。`0.0` 和 `20000` 是同一件事的两个版本号。

**影响**：判据只用 `54 <= PI < 448`，而 ch0..447 那把梯子 A 与 B 逐道完全一致，
所以科学上无害。但加载器原先要求溢出道 `E_MAX == 20000`，把 A 星全部 4,609 小时
一刀切掉了（实测 2024-01-11 试跑 `searched_hours: 0`，3 小时报 corrupt、21 小时无文件）。
已由统筹放宽为「20000 或 0.0」，梯子那几条校验一条没松。
