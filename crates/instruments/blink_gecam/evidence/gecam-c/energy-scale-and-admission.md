# GECAM-C 的能量刻度与准入口径

本轮（2026-09-11）在 IHEP 集群上对 GECAM-C 归档直接统计的结果，回答
OPEN-QUESTIONS 第 17、19 条里与能量刻度有关的三个未决项，并带出一个先前
没人查过的口径缺口。凡"实测"字样都指对归档文件的直接统计，脚本见本目录。

## 一、GECAM-C 在头两个半月用的是另一把能量梯（896 道），现有二进制整小时拒收

**现象。** `gc_ladder_scan.py` 逐小时只读 EBOUNDS（不碰事例流），全任务
19,624 个小时文件（同一小时取最大版本号）分成**干净的两类，没有第三类**：

| EBOUNDS 行数 | ch0 | ch54 | 梯顶 | 40 keV 落在 | 失败的闸 | 小时数 |
|---|---|---|---|---|---|---|
| **470** | 2.00–2.18 keV | 39.118–40.177 | ch447 = 9921–10053.5 | **ch54** | 无 | 2022 年 2,107 + 2025 年 779 + … |
| **896** | 2.00–2.09 keV | 14.163–14.542 | ch895 = 9987–10053.5 | **ch109** | `tail`\|`sentinel`\|`minch` | **1,121** |

两把梯子覆盖同一个能量范围（2.00 keV .. 10053.5 keV），**896 道那把正好细
一倍**（`ch_896 ≈ 2 × ch_470`，例如 896 梯的 ch447 = 511.0–514.4 keV 对应
470 梯的 ch223 上下）。**头（ch0 = 2.00 keV）与梯内连续性两道闸在两个版本上
都过，一条都没失败**——它们都是干净连续的梯子，只是长度不同。

**边界不是一个日期，是一段并存期。**

```
896 道：1,121 小时 / 58 天，2022-08-03 .. 2022-10-15   （归档里最早的一天就是 2022-08-03）
470 道：2,107 小时 / 93 天，2022-09-21 起；2022-10-16 之后全是它
两把并存的天：2022-09-21 (896:5 / 470:19)、09-22 (19/5)、09-30 (23/1)、
              10-14 (9/15)、10-15 (14/10)
```

**是逐小时切换，不是一刀切。**

**896 道版本的完整口径**（实测 2022-08-15 02h，12 路 GRD）：

* 能阈 `MIN_CHANNEL = 54` 在这把梯子上是 **14.16–14.54 keV**，不是 40 keV；
  40 keV 落在 **ch109**。
* 准入上界 `PI < 448` 在这把梯子上是 **514 keV**，不是 10 MeV。
* **溢出哨兵从 ch896 起，而 EBOUNDS 只有 896 行——哨兵行不在表里。**
  `EVT_TYPE == 2` 的事例其 PI 逐路逐档只有一个取值：896/897/…/907 是 12 路
  高增益、908/…/917 是低增益（d06 与 d12 没有低增益支路）。470 道版本里同一批
  哨兵行是在表里的（448..469）。
* `EVT_TYPE == 1` 的 PI **从不 ≥ 896**（逐路逐档 0.00%），与 470 版"type1
  从不 ≥ 448"同构。

**现有二进制的行为是正确的。** `EboundsHdu::verify` 的尾部闸要求 ch447 的
`E_MAX` 是 10053.5，896 梯在那里是 514.44，于是整小时报 `corrupt_data`。
**这是闸门正确动作**——照搬道号阈值会把能窗整个搬错位（14 keV 以上全收、
514 keV 封顶）。但没人量过它关掉多少曝光：**1,121 小时 ≈ 703 小时活时间
≈ 29 天曝光**（按实测占空比 0.627），**全部落在 WWLLN 覆盖内**。相对全任务
可搜曝光（约 483 天）是 +6%，但对 2022-08 .. 2022-10 这一段是从零到全部。

**建议的修法：两个常数都从 EBOUNDS 自己推，不写死版本号。**

* **梯长** = 从 ch0 起 `E_MAX[k-1] == E_MIN[k]` 一路连续到断开为止的长度；
  断不掉就取表的行数。470 版在 448 断（ch447 `E_MAX` 10053.5 → ch448
  `E_MIN` 369.87），896 版不断 → 梯长 896。**同一条规则两个版本都对。**
* **能阈道** = `channel_above(40 keV)`。`EboundsHdu` 已经在算这个值，现在只是
  拿它跟写死的 54 比对然后报错；改成直接用它。
* **不动的闸**：ch0 = 2.00 keV、梯内连续、**梯顶 = 10053.5 keV**。最后这条
  两个版本都过（470 版在 ch447、896 版在 ch895），它才是真正护住能量刻度的
  那道闸，只是索引要跟着梯长走。

**已按这个修法实现（2026-09-11）**，见 OPEN-QUESTIONS 第 21 条。核对过的
六个 epoch（`gc_probe_ladder.py`，按新规则现算，不认行数也不认版本号）：

```
gcg_evt_220921_00  行 896  梯长 896  ch0=2.00-2.089  梯顶 10053.5  能阈道 109  表尾无溢出块
gcg_evt_221015_12  行 896  梯长 896  ch0=2.00-2.089  梯顶 10053.5  能阈道 109  表尾无溢出块
gcg_evt_221016_12  行 470  梯长 448  ch0=2.00-2.183  梯顶 10053.5  能阈道  54  e_max[448]=20000
gcg_evt_230615_12  行 470  梯长 448  ch0=2.00-2.183  梯顶 10053.5  能阈道  54  e_max[448]=20000
gcg_evt_250205_02  行 470  梯长 448  ch0=2.00-2.183  梯顶 10053.5  能阈道  54  e_max[448]=20000
```

**这把细梯只有 GECAM-C 有，而证据来自 B 星不是 A 星**（`gc_ladder_rows.py`）：
A 星第一天有数据是 2022-10-21，比细梯结束（10-15）晚 6 天，**它根本没有那个
纪元的数据**，所以"A 星逐日 965 个文件全是 470 行"是零信息。真正排除掉
"任务级改版"的是 **B 星覆盖了 2022-08..09 而全程 470 行**。

## 二、EBOUNDS 溢出段每一行的 `E_MIN` 就是那条支路的满量程能量

这条先前没人用过，它把"从数据求满量程道"和"从标定表查满量程道"两条独立
路子对上了，**比任何单独一条都硬**。

**把行钉到 (探头, 增益) 不靠猜**：事例表里 `EVT_TYPE == 2` 的事例，其 PI
就是该支路那一行的行号，**逐路逐档只有一个取值**（实测 22 个组合全部唯一）。
C 星 470 道版本的 22 行 = 12 路高增益（ch448..459）+ 10 路低增益
（ch460..469），**d06 与 d12 没有低增益支路，所以是 22 不是 24**。

**声明值 vs 实测值**（`gc_fullscale_xcheck.py`；实测 `edge` = `EVT_TYPE == 1`
的 PI 直方图里最后一个计数 ≥ 10 的道，再用梯子折成能量）：

| epoch | 高增益 r | 高增益 实测/声明 | 低增益 r | 低增益 实测/声明 |
|---|---|---|---|---|
| 2023-06-15 12h | +0.969 | 中位 0.867（极差 0.181） | **+0.9992** | **中位 0.943（极差 0.020）** |
| 2024-03-10 02h | +0.977 | 中位 0.867（极差 0.172） | **+0.9992** | **中位 0.943（极差 0.020）** |

声明的满量程横跨 250–465 keV（高增益）与 4.9–7.6 MeV（低增益），也就是逐路
差 1.9 倍与 1.5 倍，**在这么大的杠杆上实测值仍然逐路跟着走**。低增益那一列的
"实测/声明"在 10 路上只散布 0.020，**这不是相关，是同一个量的两次测量**。

**后果**：满量程道不必查 CALDB——**EBOUNDS 自己带着这张表，逐小时随文件走，
标定再更新一次也自动跟上**。这同时回答了 GECAM-A 那边"要不要做静态逐探头
上限表"：不用做，查表就是查 EBOUNDS。

**一条估计量的陷阱，记下来免得别人再踩。** `edge`（最后一个 ≥ 10 计数的道）
**不是尺度无关的**：2025-02-05 02h 那个小时逐路只有 1.1–4.0 万个事例（2023 年
同类小时是 100–200 万），于是低增益的 `edge` 掉到 ch324–339、"实测/声明"
看着从 0.943 塌到 0.26–0.49。**那是统计量不够，不是满量程变了**——同一批
事例的 `PI` 最大值仍是 383–419，与 2023 年的 389–422 同档。要跨小时比较
`edge`，阈值必须随该支路的总计数缩放，或者直接用不依赖阈值的分位数。

## 三、OPEN-QUESTIONS 第 19 条：C 星没有 A 星那个超量程堆积包，A 星那套准入上界修正不该推广

逐探头逐增益从 PI 直方图求 `edge`（`gc_edge.py`，从数据自己求，不查表），
5 个 epoch × 每天 3 个过境：

| epoch | 高增益 edge 中位 / 逐路范围 | 包抬升中位 | 低增益 edge 中位 / 范围 | 包抬升中位 |
|---|---|---|---|---|
| 2023-01-30 | 190–198 / 175–243 | 0.55–0.64 | 406 / 385–415 | 1.21–1.47 |
| 2023-06-15 | 189–196 / 161–208 | 0.56–0.62 | 410 / 389–422 | 1.27–1.74 |
| 2023-11-02 | 189–190 / 161–202 | 0.53–0.60 | 410 / 389–422 | 1.27–1.93 |
| 2024-03-10 | 189–190 / 161–202 | 0.49–0.66 | 410 / 389–421 | 1.61–2.00 |

（"包抬升" = 悬崖下 20 道里的峰 / 更低处平台的中位。）

**四条结论：**

1. **`EVT_TYPE == 1` 里 `PI >= 448` 逐路逐档是 0.000%**，5 个 epoch 无一例外。
   **`Event::keep` 里 `PI < 448` 这半个准入条件在 C 星上同样是空转**，与
   GECAM-A 上的结论一致。
2. **高增益档没有堆积包。** 包抬升 0.49–0.66，**全部小于 1**——悬崖下 20 道
   反而比更低处的平台还低，那是谱本身在落，不是堆积。
3. **低增益档有，但很弱。** 包抬升中位 1.2–2.0，而 GECAM-A 低增益是
   **12.8–14.4 倍**。**C 星弱一个数量级。**
4. **逐过境不漂。** 同一天三个过境的 `edge` 差 ≤ 2 道；2023-06 / 2023-11 /
   2024-03 三个 epoch 的中位全是 189–196（高）与 410（低）。只有 2023-01 的
   低增益是 406，与后面差 4 道。**GECAM-A 那个"2023-06-16 h16 整仪器偏 9 道"
   的逐过境漂移在 C 星未观察到。**

机制上说得通，而且与第二节自洽：A 星 2022–2024 段没有在轨 EC，默认标定把
满量程压到 ch379，**于是超量程沉积堆在 ch368–383、整个落在 `PI < 448` 的
准入窗里**；C 星的满量程道（高 161–208、低 385–422）也都在 448 以下，但
**C 星的超量程沉积有地方去**——它们被判成 `EVT_TYPE == 2` 并写进哨兵道，
不进 `keep`。

**所以 A 星那条"准入上界要收到 `edge − margin`"的修正不推广到 C。** C 星
要收的话，能收到的只有低增益档悬崖下 15 道里那一小撮（占该档计数 0.2–8.8%、
占全部准入计数 0.1–2.9%），而那一段的抬升只有 1.2–2.0 倍，**扣不扣对谱学
结论都不改方向**。

## 四、OPEN-QUESTIONS 第 17 条：两档的 PI 是同一把尺子，能阈不受"去重留哪条"影响

**配对口径先说清楚。** Rust 侧 `dedupe_gain_pairs` 现在按**同探头 + 死时间窗内
+ 增益一高一低**配对，不再要求时戳相等。两个口径在 C 星上的差别是实打实的
（2023-06-15 12h，12 路全量）：

```
死时间口径   1,735,222 对（占原始事例 17.38%）
时戳相等     1,325,000 对（占原始事例 6.635%，与旧文档那个数逐位相同）
→ 死时间口径多配 31%；对内 |dt| 中位 0、p90 104.3 ns、p99 208.6 ns
→ dt == 0 的占 76.35%，也就是 23.65% 的对时戳不相等
```

**偶然配对必须一起报。** 对照做法：把低增益支路的时戳整体平移 0.37 s
（远大于死时间、远小于轨道尺度）再配一次，配到的全是偶然的。

```
死时间口径   偶然 72,237 / 1,735,222 = 4.16%
时戳相等     偶然     18 / 1,324,865 = 0.0014%
```

于是 **dt > 0 的那 410,357 对里偶然的占 17.6%**（= 72,237/410,357，
Wilson 95% 区间 17.5–17.7%，分母是**全小时**不是候选窗）。这个数要记住：
**去重不是零代价的，宽窗换来的多配里有六分之一是误并。** 候选窗内事例密度
高几个数量级，那里的偶然率必须另外量——**已量，见第七节，窗内是 31–36%**。

`DEAD_TIME` 这一列在 C 星**不是常数**（GECAM-A 是逐路恒为 4）。实测取值上百个，
量化步 0.8 µs，**分两族**：短族 4.0–6.4 µs，长族 69.6–204.0 µs，中间是空的。
去重窗最宽能到 204 µs，这就是 4.16% 偶然率的来源。

**两档是不是同一把尺子：用同时戳对做，判别量是"脱离对角线的位置"**
（`gc_gainscale3.py`；同时戳对偶然率 0.0014%，可以当纯样本）。1,324,865 对
里两条都是 `EVT_TYPE == 1` 的有 86,401 对（6.52%）——**其余的高增益那条已经
进了哨兵道**，所以能比刻度的只有这 6.52%。

```
PI_lo    n        PI_hi 中位    差     能量比 E(hi)/E(lo)
 120     330       127.0      +2.0      1.027
 130    1289       133.0      -2.0      0.975
 150    5525       150.0      -5.0      0.946
 170   12396       165.0     -10.0      0.882
 180   14121       171.0     -14.0      0.833
 190   12480       171.0     -24.0      0.728
 200   11121       167.0     -38.0      0.606
 220    5606       174.0     -51.0      0.507
 240     339       176.0     -69.0      0.399
```

**在两档都在量程内的那一段（`PI_lo` 120–150，约 130–200 keV），两档读数相差
2–5 道、能量比 0.95–1.03，而且差值的符号在 `PI_lo ≈ 130` 处过零**——在这个
测量的精度内，**它们是同一把尺子**。`PI_lo` 超过 160 之后高增益读数迅速落后
并在 ch167–178 上封顶，那个封顶值正落在逐路 `edge_hi`（161–208）当中，
**是高增益支路见顶，不是刻度不同**。

**但"见顶压缩"这个解释本身没验成，要说清楚。** 判别办法是看逐路的脱离点
是否随各自的 `edge_hi` 走（同一把尺子 + 见顶 → 斜率 ≈ +1；两把尺子 → 无关）。
实测只有 6 路样本够（其余几路在该道段的对数只有 11–175），**r = +0.438、
斜率 +0.65、脱离点/`edge_hi` 在 0.804–1.000 之间散布**。n = 6 的 r = +0.44
远不显著，**这个检验没有功效，排除不掉一个温和的刻度差**。记成"未验成"。

**真正让这条不影响判据的，是另一个实测事实：低增益支路根本够不到 ch54。**
逐路逐 epoch 实测低增益 `EVT_TYPE == 1` 的最小 PI：

```
2023-06-15 12h   113 / 122 / 123 / 125 / 131 / 138 / 144 / 159 / 171 / 172 / 174
2025-02-05 02h   166 / 175 / 181 / 182 / 182 / 187 / 191 / 191
```

**最小值 113，比 ch54 高一倍。** 也就是说 `MIN_CHANNEL = 54` 这道阈**永远只
作用在高增益记录上**，去重保留低增益那条**改变的是能量不是计数，更不改变
能阈**。而保留低增益是对的：高增益支路在 ch167–178 就封顶，留它会把
215 keV 以上的信息整段丢掉。

## 五、一小时完好的 GRD 数据会被一个 CPD 占位文件拖死（20 小时，可修）

`gc_manifest.py` 的事后硬断言（"产出小时数 == 应有小时数，不等就非零退出"）
抓到一处：30 天里应有 655 个可搜小时，实得 654，差在 **2023-01-30 03h**，
搜索报 `corrupt_data: Cannot find column "TIME"`。

逐文件点下去，**坏的不是 GRD**：

```
GRD  gcg_evt_230130_03_v00.fits    86,400 字节   EVENTS 表零行零列（空壳）
     gcg_evt_230130_03_v01.fits   269 MB       EVENTS01 7 列 1,481,157 行  ← 版本选择正确取了它
CPD  gcc_evt_230130_03_v00.fits    28,800 字节   两个 EVENTS 表零行零列（只有这一个版本）
```

**一小时完好的 GRD 数据（1,481 万事例）因为 CPD 是占位文件而整个丢掉。**
`from_epoch` 的规则是「只放过找不到文件；文件在却读坏了仍旧报错」，**空壳被
算进了后一类**。

空壳与真正的损坏形态上分得开：空壳是零行、**零列**（`EVENTS` 表连列定义都没有），
不是读到一半是乱码。全任务点一遍（`gc_stub_scan.py`，判据是最大版本的第一个
`EVENTS` 表有没有列）：

```
CPD 空壳（零列） 217 小时      GRD 空壳（零列） 206 小时
**CPD 空壳、而同一小时 GRD 是好文件（> 1 MB）的：20 小时**
```

**那 20 小时（占全任务 0.10%）是白丢的**，逐条清单在 `gc_stub.csv`。建议的窄修法：
**CPD 文件存在但 `EVENTS` 表零列/零行 → 与「找不到 CPD 文件」同等对待**（降级成
这一小时没有 CPD，`acd = None`，GRD 照常搜）；**GRD 空壳必须照旧致命**——没有
事例就没有搜索。修改搜索语义由统筹报 `main`，本文件只给量。

顺带这条也正面验证了版本号解析那个修复：03h 的 GRD 有 v00（空壳）与 v01（好的）
两个版本，**取到的是 v01**。

## 六、`-mem` 实测

## 七、窗内的偶然配对率是全小时那个数的七八倍（2026-09-11）

第四节末尾留了一句"候选窗内事例密度高几个数量级，那里的偶然率必须另外量"。
量出来了：**窗内 31–33%，全小时 4.16%**。

**平移对照在窗内用不了，这是系统问题不是精度问题。** 全小时那个 4.16% 是把
低增益支路整体平移 0.37 s 再配一次量出来的。同样的手法搬到候选窗里会量错：
平移之后窗里剩下的是暴发的高增益那一半，加上从别处（0.37 s 之外）飘进来的
低增益本底——**窗内密度被平移这个动作本身破坏了**，量到的是本底密度下的偶然率。

换成**窗内均匀重抽**，事例数、窗长、探头与增益的边缘分布全部原样保留，
只有时间上的符合结构被打掉：

* **真**：窗内通过准入的原始事例，按死时间口径逐探头配对（与 Rust 侧
  `dedupe_gain_pairs` 同规则，同探头是硬前提），数两条都落在窗内的对；
* **偶然**：同一批事例的时戳在同一个窗内均匀重抽，标签跟着事例走，再配一次。

**先对账再信任何重算的数**（`gc_dupe_inwindow.py`）：去重后窗内剩下的事例数
与搜索报的 `count` 逐条比，**2023-04-12 是 653/653 = 100.00%，2023-01-06 是
1254/1255 = 99.92%**。口径对上了，下面的数才有意义。

```
                        2023-04-12      2023-01-06      2023-07-17
候选窗                     653            1255             882
对账（== 搜索报的 count） 653/653        1254/1255        881/882
                         100.00%         99.92%          99.89%
窗内原始事例               6096           11741            9064
窗内密度                7.87e4 c/s      7.71e4 c/s      7.99e4 c/s
双增益  窗内真配对          297             554             415
        窗内偶然           93.1           180.2           149.3
        **偶然占比       31.34%          32.53%          35.97%**   （全小时 4.16%）
        每窗误并          0.143 条        0.144 条        0.169 条 → 窗内计数被压低 1.6–1.7%
跨探头 τ=150ns 真配对      3161            6003            4348
        窗内偶然          697.6          1310.6          1165.1
        **偶然占比       22.07%          21.83%          26.80%**
```

**三天独立给出同一个数**（双增益 31–36%，跨探头 22–27%），而且它们的窗内密度
也几乎相同（7.7–8.0e4 c/s）——这不是巧合，密度就是这个量的唯一驱动。

**这个偶然数是下界，方向单向。** 重抽假定事例在窗内均匀，而候选窗是搜索挑出来
的最佳格，窗内本身可能还有更陡的结构；结构越陡，偶然配对只会更多。**下界有多松
不靠猜，用密度对照量出来**（2023-07-17）：

```
                        密度 ×2（撒在半个窗）   本体     密度 ÷10（撒在十个窗）
双增益  偶然对              217.2             149.3            69.6
        占真配对           52.33%            35.97%          16.76%
跨探头  偶然对             1313.3            1165.1           677.9
        占真配对           30.20%            26.80%          15.59%
```

**十倍那一档同时是这个估计量的灵敏度检验，它过了**：密度降十倍，双增益偶然对
掉到 0.47 倍、跨探头掉到 0.58 倍。**偶然数若不随密度动，这个测量就根本没有
分辨力**——它动了。

**两个量对密度的敏感程度差很多，原因是窗长。** 密度翻倍时双增益偶然占比涨
45%（36% → 52%），跨探头只涨 13%（26.8% → 30.2%）。**跨探头那一档被短窗主导**：
C 星有约一成候选的窗比 1 µs 还短，整窗都在 τ = 150 ns 的几倍之内，撒哪儿都成对，
**「偶然」这个词在那里没有意义**——把它们和长窗平均在一起会得到一个没法解释的数，
所以后续按窗长 ≤ 1 µs / > 1 µs 分两档报（脚本已支持）。

**后果，按用途分开说：**

* **对计数**：每窗误并 0.14 条，窗内计数被压低 **1.6%**。量小，不改任何结论的
  方向，但**去重不是零代价**这件事要写在口径里。
* **对 τ = 150 ns 跨探头合并**（OPEN-QUESTIONS 第 22 条那四道门槛里的第 3 条）：
  在真候选窗里，**合并掉的对当中至少 22–27% 是偶然的**。这与第 22 条禁止用解析式
  `1 − exp(−nτ/W)` 的理由是同一件事——**均匀撒点是下界**，而真 TGF 的光子比
  均匀更挤，损失率只会更高。所以这个 22–27% 不能当成"代价上限"，它是下限，
  **而密度对照给了下界的松紧：密度翻倍它涨到 30.2%**。

**τ 不随量化步 q 变。** 底下是双增益两支路之间一个约 100 ns 的电子学固定延迟
（第 32 条），q 只决定它落在哪一格；若把 τ 改成 q 的倍数，C 星（q = 7.45/14.9 ns）
的 τ 会缩到 30–60 ns，连那条线都盖不住。
